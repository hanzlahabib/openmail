## T32 approval-seal  Owns: crates/openmail-smtp/**, crates/openmail-security/**
Fix F2. Make it impossible to send without a verifier-consumed approval: define in `openmail-smtp` a sealed capability `ApprovalProof` with NO public constructor from caller-supplied data; the only way to obtain one is via a trait `ApprovalConsumer` (defined in smtp) that security implements: `fn consume(&self, principal, account, &SendRequestDescriptor, token) -> Result<ApprovalProof>` where the descriptor is derived by smtp from the actual SendRequest (account, normalized to/cc/bcc, subject, content hash incl. attachments). Unify binding fields so the security approval binds exactly: principal/client, account, normalized recipients (to+cc+bcc), subject, smtp content hash, attachment hashes, expiry, single-use id. `SmtpClient::send` takes the sealed proof; tests: send without approval impossible at compile time (doc-test `compile_fail`), mismatched recipients/subject/content/attachment hash rejected, expired, replayed token rejected after first consume (persisted across reopening the SQLite store), wrong principal rejected, approval minted for request A cannot send request B. Dependency direction: security may depend on smtp (to implement the trait) OR define the trait in core — choose the option with no cycle and document it in docs/DECISIONS.md style notes in crates/openmail-smtp/NOTES.md. Keep an out-of-band `ApprovalGrantor` for minting approvals (never reachable from an MCP tool).
